# AegisCode 三分钟项目介绍与 Agent 岗面试题

> 项目名称：AegisCode；仓库名称：AegisAgent。
>
> 适用岗位：Agent 应用开发、AI Coding Agent、LLM 应用工程、智能研发平台。
>
> 使用原则：先讲当前代码已经实现并验收的能力，再讲可选部署和历史版本。未经压测或真实商业模型联调的数据，不作为当前版本结论。

## 一、项目定位

### 一句话介绍

AegisCode 是一个面向个人与企业的持久化 AI Coding Agent 工作台，通过受控 Query Loop、原生工具调用、长期记忆、Skill 生命周期、中心化多 Agent、模型容错和权限审查，让长任务具备可恢复、可验证、可审计的执行闭环。

### 当前核心技术栈

- Agent 内核：Python 3.12、原生 Tool Calling、Query Loop、ReAct、Plan 回退、Reflection。
- 服务与状态：FastAPI、Pydantic、SQLAlchemy Async、PostgreSQL；个人版可使用 SQLite WAL。
- 模型接入：OpenAI、自定义 OpenAI 兼容接口、Anthropic、Azure OpenAI、Ollama。
- 检索与知识：持久化 BM25；可选 Milvus、向量模型和 Cross-Encoder 重排。
- 工具生态：MCP 官方客户端、Docker 隔离执行服务、受控 Git Fork/Worktree。
- 前端与交付：TypeScript、Vite、HTML、CSS、SSE、Docker、wheel、Windows EXE/Setup。
- 工程保障：数据库租约、幂等键、断点恢复、三态熔断、限流、负例测试和 Trace ID。
- 设计参考：Hermes Agent 的个人记忆与按需技能复用思路；Hermes 是设计参考，没有作为项目运行库接入。

### 与简历旧技术栈的关系

项目早期简历可保留 `FastAPI、LangChain、LangGraph、Milvus、Redis、PostgreSQL、Docker`，但面试时应主动说明：当前主执行链已经收敛为自研轻量 Harness，不再把 LangChain/LangGraph 和 Redis 作为默认运行依赖。这样能避免“简历写了但仓库依赖不存在”的追问风险。

LangChain/LangGraph 适合快速验证图编排，Redis 适合分布式缓存和短期会话；当前版本为了强化执行语义、审批绑定、工具账本和断点恢复，核心状态统一落在 SQL 数据库，Milvus 则作为可选混合检索后端。

## 二、三分钟口述版

大家好，我的项目叫 AegisCode，是一个参考 Claude Code Harness 思路实现的个人与企业级 AI Coding Agent。它解决的不是“让模型回答一次问题”，而是让 Agent 在真实任务中持续调用工具、保存状态、处理中断，并且能够证明自己做过什么。

第一部分是执行内核。我基于 FastAPI 和异步 Python 实现了 Query Loop，支持 ReAct、Plan 和 Reflection 三种运行模式。复杂任务可以先生成结构化计划，计划解析失败会记录原因并回退 ReAct；每个任务默认最多 10 步，同时限制模型调用并发、运行时间、用户活动任务数和全局并发，避免 Agent 无限循环。

工具调用采用模型原生协议，调用前写入工具账本，执行后再保存结果；危险工具必须人工审批，审批与任务、调用编号和参数哈希绑定，不能改完参数继续复用。

第二部分是中心化多 Agent。我没有让子 Agent 相互自由通信，而是由主 Agent 统一规划、分配预算、审批和汇总。系统支持 Team 独立上下文、Fork 继承有界会话，以及批准后准备 Git Fork/Worktree 代码目录。子任务最多两个，只拿到父权限的只读子集；依赖图只有前驱通过工具账本验收后才放行后继。子 Agent 即使在回答里声称“测试通过”，如果没有必需工具的完成记录，也不能通过独立验收。

第三部分是记忆、Skill 和上下文治理。系统会把用户偏好、约束、任务经历、失败步骤和工具证据沉淀成草稿资产，登录时加载已激活的偏好与约束，执行时再按任务召回相关记忆和 Skill。Skill 采用候选、启用、退役和版本恢复的生命周期；失败任务可以生成 Skill 候选，但必须经过用户反馈或独立证据验证，不能让一次错误直接污染能力库。

大工具结果不会全部塞进提示词，而是保存为 Artifact，只注入预览和引用，需要时再按权限读取；上下文裁剪按完整的 assistant/tool 消息组进行，避免破坏工具调用配对。历史提示只记录裁剪数量与边界，目前没有实现内容摘要压缩。

第四部分是可用性和安全。模型层支持 OpenAI、自定义兼容接口、Anthropic、Azure 和 Ollama，通过优先级、同级权重、并发信号量和按“端点+模型”隔离的三态熔断实现自动降级，默认恢复探测窗口是 60 秒。任务状态通过数据库租约、心跳和幂等键持久化；SSE 使用事件游标和 Last-Event-ID 断点重连，断网只重放事件，不会重新执行任务。

MCP 只允许运维白名单中的服务器和工具，Docker 沙箱不可用时直接拒绝执行，不降级到宿主机；用户、租户、角色、文件路径和资产查询都在服务端校验。

这个项目最能体现我与岗位匹配的地方，是我不仅接过模型 API，还完整处理了 Agent Loop、上下文、工具协议、失败恢复、结果验收、多模型路由、Coding 工作区和安全边界。最近一次完整代码回归记录为 393 项通过、1 项因 Windows 符号链接权限跳过；商业模型实网效果、真实 Milvus 召回质量和生产压测仍需要用固定数据集继续验证，我不会把协议测试等同于线上指标。

## 三、简历亮点建议稿

### 项目简介

参考 Claude Code Harness 设计并实现 AegisCode，基于 Query Loop 与原生 Tool Calling 构建持久化任务闭环，覆盖中心化多 Agent、Skill 演进、长期记忆、分层上下文、多模型容错、MCP 工具接入、代码工作区与权限安全审查，支持源码、Docker、wheel 和 Windows 安装包交付。

### 项目职责与成果

- **中心化多 Agent 协作：** 主 Agent 统一规划、预算、审批、验收与汇总，子 Agent 仅获得只读工具和父权限子集；支持 Team、Fork 以及批准后的 Git Fork/Worktree，加入两节点依赖图和独立工具账本验收门，防止子 Agent 仅靠文本声称完成。
- **Skill 与受控自进化：** 建立 Tool、Skill、Skill 目录三级能力结构，按作用域、状态、工具权限、元信息和正文匹配进行两阶段召回；将成功流程、失败步骤、用户偏好和约束沉淀为可追溯草稿，支持审核启用、反馈验证、指纹去重、版本恢复和退役。
- **任务状态与失败恢复：** 实现默认 10 步的 ReAct/Plan/Reflection 循环，Plan 失败自动回退；以数据库租约、心跳、工具 started/done 账本和幂等键保障任务恢复，未知副作用进入 interrupted 并要求人工核对，避免危险操作自动重放。
- **多模型高可用：** 接入 OpenAI、自定义兼容接口、Anthropic、Azure OpenAI 和 Ollama，以优先级、权重和并发预算路由；为每个端点与模型维护 Closed/Open/Half-Open 三态熔断，默认 60 秒后有限试探，首选失败自动切换候选模型。
- **上下文与长期记忆：** 登录加载用户已启用的偏好和约束，任务阶段按需召回记忆与 Skill；将大工具结果外置为 Artifact，以预览、引用和按需读取替代全量注入，并按完整工具消息组裁剪上下文，降低长会话失配和 Token 浪费。
- **权限与安全隔离：** 实现租户、用户和角色三层私有范围，令牌哈希存储；MCP 使用服务器/工具/租户/用户白名单和参数 Schema 校验，代码执行仅进入 Docker 隔离服务；针对路径穿越、Windows 尾点/空格别名、ADS、`.git`、符号链接和越权访问建立负例测试。
- **知识检索与工程交付：** 默认使用持久化 BM25，在配置完整时启用 Milvus 向量召回、RRF 融合和 Cross-Encoder 重排，向量链路异常时保留 BM25 证据；提供 TypeScript 企业工作台、SSE 重连、Docker、wheel、便携包和 Windows Setup。

## 五、30 道高概率面试题与 STAR 回答

### 1. 请用三分钟介绍这个项目

**精简回答：** AegisCode 是持久化 AI Coding Agent 工作台。我实现了有界 Agent Loop、原生工具调用、中心化多 Agent、记忆与 Skill 生命周期、多模型熔断降级、数据库断点恢复和多层权限审查，重点解决长任务“能执行、能恢复、能验证、能审计”的问题。

**STAR 详细回答：**

- **S：** 普通聊天接口只能完成一次请求，面对长任务会出现上下文膨胀、工具重复执行、断线丢状态和权限失控。
- **T：** 我需要把模型调用改造成企业可控的任务系统，同时兼顾个人版安装成本。
- **A：** 我用 FastAPI 和数据库状态机实现 ReAct/Plan/Reflection 循环，以工具账本、审批哈希和租约管理副作用；再加入长期记忆、Skill 草稿审核、多 Agent 依赖图、模型路由和 SSE 重连。
- **R：** 项目形成了从任务创建到执行、证据、反馈和能力沉淀的闭环；最近完整回归记录为 393 项通过、1 项环境权限跳过，并可通过源码、Docker、wheel 和 Windows 安装包交付。

**可追问证据：** `app/harness/runtime.py`、`service.py`、`store.py`、`app/api/routes/harness.py`。

### 2. 为什么当前版本没有直接使用 LangGraph？

**精简回答：** LangGraph 适合快速搭建状态图，但这个项目后期的难点是数据库租约、审批参数绑定、未知副作用、SSE 重放和多租户边界。我选择自研轻量 Harness，让状态迁移和事务语义能够直接落到数据库并被测试验证。

**STAR 详细回答：**

- **S：** 早期技术栈包含 LangChain/LangGraph，但业务开始要求断点恢复、幂等、审批和并发 Worker。
- **T：** 需要决定继续在框架回调中叠加规则，还是收敛成可审计的执行内核。
- **A：** 我保留 ReAct、Plan、工具调用等模式，但把 Run、Event、ToolCall、Asset 显式建模，用条件更新和事务表达领取、心跳、审批和终态。
- **R：** 核心行为可以通过数据库记录复现和测试，依赖更轻；代价是编排、持久化和恢复都需要自行维护，因此文档不会宣称框架能力仍在当前主链路中。

**可追问证据：** `pyproject.toml` 当前无 LangChain/LangGraph 运行依赖；核心表在 `app/harness/models.py`。

### 3. Agent Loop 是怎样工作的？

**精简回答：** Worker 从数据库领取任务，构造受限上下文，请求模型；模型返回工具调用时先落账本，再做权限、风险和审批检查，执行后把结果追加到消息并进入下一轮，直到产生最终答案或触发步数、时间、取消等停止条件。

**STAR 详细回答：**

- **S：** 无界 while-loop 容易造成 Token 和费用失控，也无法确定工具是否已执行。
- **T：** 建立有状态、有预算、可恢复的循环。
- **A：** 默认限制每任务 10 步、服务级同时 6 个模型调用和每任务 300 秒运行时间；每轮保存 messages、step 和事件，工具记录 started/done，取消和超时在边界检查。
- **R：** 循环不依赖进程内内存才能解释状态；重启后可根据租约和账本恢复，未知副作用不会自动重放。

**可追问证据：** `HarnessSettings.max_steps`、`Worker.react()`、`Worker.execute_tool()`。

### 4. ReAct、Plan 和 Reflection 三种模式如何取舍？

**精简回答：** ReAct 适合目标清晰、边执行边观察；Plan 适合多步骤任务，先要求模型返回结构化步骤，解析失败记录 `plan_fallback` 后继续 ReAct；Reflection 在答案前增加一次受预算约束的证据复核，不允许无限自我反思。

**STAR 详细回答：**

- **S：** 单一路径无法兼顾简单任务延迟和复杂任务稳定性。
- **T：** 让策略可选，同时保证失败时任务还能推进。
- **A：** 服务端校验模式；Plan 只规划一次并验证 JSON 结构，异常回退；Reflection 只有剩余步数且功能开启时执行一次验证。
- **R：** 简单任务不承担额外规划成本，复杂任务获得显式步骤，规划器失败也不会让整个请求直接失败。

**可追问证据：** `app/harness/runtime.py` 中 `plan`、`plan_fallback`、`reflection` 事件。

### 5. 如何防止 Agent 无限调用工具？

**精简回答：** 我从步数、总时长、模型调用并发、用户活动任务数、子任务数和工具独立超时六个维度设预算；剩余预算不足时停止，而不是依赖模型自行收敛。

**STAR 详细回答：**

- **S：** 模型可能重复调用同一工具，或在错误结果上持续尝试。
- **T：** 让成本和失败上界可计算。
- **A：** 设置最大 10 步、任务 300 秒、模型超时 45 秒、每用户最多 4 个活动任务、最多 2 个子任务；工具调用参数规范化后建立哈希和唯一账本。
- **R：** 循环一定在预算内终止；重复完成的工具结果可识别，未知副作用则转入人工核对。

**可追问证据：** `app/harness/settings.py`、`models.ToolCall` 唯一约束。

### 6. 为什么采用中心化多 Agent？

**精简回答：** Coding 场景更需要确定的权限、预算和验收。主 Agent 持有控制权，子 Agent 只是受控工具调用，减少身份传递、状态同步和子 Agent 相互误导的问题。

**STAR 详细回答：**

- **S：** 自由通信的多 Agent 很容易产生循环委派、权限扩散和上下文爆炸。
- **T：** 在获得并行分析收益的同时保持安全边界。
- **A：** 主 Agent 解析最多两个节点的任务图，分配步数和时间；子 Agent 只能使用只读工具，不能继续委派、写文件或调用外部 MCP，最终由主 Agent 汇总。
- **R：** 根节点可以并行执行，依赖节点按验收放行；协调状态仍集中在父任务和数据库中，不需要额外消息总线。

**可追问证据：** `app/harness_tools/delegation.py` 的 `READ_ONLY_TOOLS` 和预算分配。

### 7. Fork、Worktree 和 Agent Team 有什么区别？

**精简回答：** Team 表示子 Agent 使用独立会话上下文；Fork 表示子 Agent 继承父会话的有界上下文；Worktree 不是对话模式，而是经审批后从管理员配置的 Git 仓库准备独立工作目录。三者解决的是不同层面的问题。

**STAR 详细回答：**

- **S：** “Fork/Worktree/Team”常被混用，容易把上下文复制、代码目录和协作拓扑说成同一能力。
- **T：** 给三种能力建立明确契约。
- **A：** `delegate(mode=team|fork)` 决定 session 是否继承；`project_prepare(mode=fork|worktree)` 决定 Git 目录准备方式，并必须经过审批。
- **R：** 前端和 API 能明确展示不同选项；仓库未配置时 Worktree 入口禁用，不会创建假的代码环境。

**可追问证据：** `/api/v1/capabilities`、`project.py`、`delegation.py`。

### 8. 多 Agent 的结果怎么验收？

**精简回答：** 不相信子 Agent 的自然语言自报。验收门检查真实 completed 状态、非空答案、父子归属、工具账本是否存在 started 未决项，以及 required_tools 是否有成功记录。

**STAR 详细回答：**

- **S：** 子 Agent 可以输出“测试已通过”，但实际没有读取代码或运行任何验证工具。
- **T：** 把结果可信度从文本判断提升到执行证据判断。
- **A：** 每个节点可声明必需工具；内核查询 ToolCall 完成账本，失败结果、缺失工具、跨用户父子链和未决调用均拒绝。
- **R：** 前驱未通过时后继直接 blocked；测试覆盖了伪造完成、失败工具、并行根节点和取消竞态。

**可追问证据：** `verify_collaboration_child()`、`tests/test_collaboration_contract.py`。

### 9. 如何处理并发 Worker 领取同一个任务？

**精简回答：** Worker 通过数据库事务和条件 UPDATE 竞争租约，只有成功写入 lease_owner 的实例能执行；运行中定期心跳续租，租约过期后按工具账本决定恢复还是中断。

**STAR 详细回答：**

- **S：** 多实例同时轮询时，普通“先查再改”会重复领取。
- **T：** 保证单个 Run 在一个有效租约内只由一个 Worker 推进。
- **A：** SQLite 使用 WAL、busy_timeout 和写锁，PostgreSQL 使用数据库事务；领取、续约和终态更新都带状态与 owner 条件。
- **R：** Worker 竞争和重启恢复有确定语义；这约束的是内核执行，不把外部副作用夸大成绝对 exactly-once。

**可追问证据：** `app/harness/store.py` 的 `claim()`、`running()`，`runtime.py` 的 `heartbeat()`。

### 10. 幂等和 exactly-once 有什么区别？

**精简回答：** 幂等键能保证同一用户、同一请求重复提交返回同一个 Run，内容不同则 409；但外部工具可能在执行成功后、结果落库前崩溃，所以系统不承诺 exactly-once，而是把结果标为未知并要求人工核对。

**STAR 详细回答：**

- **S：** 网络重试可能重复创建任务，进程崩溃可能发生在外部副作用和数据库提交之间。
- **T：** 分别处理“重复创建”和“未知副作用”。
- **A：** 数据库建立 `(tenant_id, owner_id, idempotency_key)` 唯一约束，并保存 payload_hash；工具先记 started，成功后记 done。
- **R：** 同键同内容复用，同键不同内容拒绝；started 未完成的危险调用进入 interrupted，避免自动重复执行。

**可追问证据：** `Run.__table_args__`、`ToolCall.__table_args__`、恢复测试。

### 11. 服务重启后任务如何恢复？

**精简回答：** 任务消息、步数、配置、事件和工具账本全部持久化；Worker 重新启动后回收过期租约。没有未决副作用的任务可重新排队，有 started 未决工具的任务进入 interrupted。

**STAR 详细回答：**

- **S：** 长任务跨越进程生命周期，纯内存状态会导致重启后丢失。
- **T：** 让恢复策略基于证据，而不是统一重跑。
- **A：** 每个步骤 checkpoint；租约附过期时间；停机先停止领取，再取消执行；父任务终止时同步清理活跃子任务。
- **R：** 已完成结果不会因重连重新生成，未知工具不会被默认为失败后重试。

**可追问证据：** `runtime.checkpoint()`、`Store.claim()` 相关逻辑、`tests/test_child_recovery.py`。

### 12. SSE 断线重连为什么不会重复执行任务？

**精简回答：** 执行和连接生命周期分离。Run 由后台 Worker 推进，SSE 只读取持久事件；客户端携带 after 或 Last-Event-ID 继续读取，因此断线只影响展示，不会重新创建或执行任务。

**STAR 详细回答：**

- **S：** 长任务常遇到浏览器刷新、代理超时或移动网络切换。
- **T：** 保证事件可续传，又不把网络重试变成业务重试。
- **A：** Event 使用自增游标，SSE 每 0.5 秒拉取新事件，定期发送 keep-alive，终态或等待审批时结束连接。
- **R：** 客户端可以去重并补齐事件；认证过期时返回专门事件，任务本身仍保留数据库状态。

**可追问证据：** `GET /runs/{run_id}/events`。

### 13. 多模型路由和熔断是怎么设计的？

**精简回答：** 模型先按优先级分组，同优先级按权重随机排序；每条“协议+端点哈希+模型”拥有独立熔断器。连续失败达到阈值后 Open，默认 60 秒后进入 Half-Open 有限试探，失败重新打开，成功关闭。

**STAR 详细回答：**

- **S：** 单模型限流或故障会放大为整个 Agent 服务不可用。
- **T：** 隔离故障并自动切换，同时避免故障端点被持续打满。
- **A：** 路由器使用信号量限制模型并发，禁用 SDK 内部重试以避免重试叠加；每个候选通过独立 CircuitBreaker 调用，失败后尝试下一候选。
- **R：** 同名模型不同端点互不污染；取消 Half-Open 探测时重新打开，不把未知探测当成功。

**可追问证据：** `model_router.py`、`circuit_breaker.py`、`test_model_protocols.py`。

### 14. 不同模型 API 如何统一工具调用？

**精简回答：** 内核使用统一的 messages、tools 和 tool_choice 结构。OpenAI/Azure/Ollama 走兼容客户端；Anthropic 适配器负责 system 分离、tool_use/tool_result 转换、结束原因和 Token 用量归一化。

**STAR 详细回答：**

- **S：** 不同厂商在 system、工具结果、结束原因和 usage 字段上不一致。
- **T：** 不让执行内核感知每个厂商的协议细节。
- **A：** 通过 Provider 配置选择客户端，把返回值统一成 `LLMResponse(content, model_id, usage, raw)`；配置校验禁止自定义参数覆盖 model、messages、tools 等保留字段。
- **R：** 同一 Agent Loop 可以在五类来源间降级；协议替身测试覆盖工具请求、工具结果、缓存 Token 和错误脱敏。

**可追问证据：** `anthropic_adapter.py`、`model_config.py`、`tests/test_model_protocols.py`。

### 15. 低延迟请求和长任务 Agent 应如何采用不同架构？

**精简回答：** 登录、能力查询等短请求走普通异步 API 和入口限流；长任务只负责快速创建 Run，实际执行交给带租约的 Worker，客户端通过 SSE 观察进度。两者不能都占用一个同步 HTTP 请求直到完成。

**STAR 详细回答：**

- **S：** LLM 和工具调用可能持续数分钟，直接挂住 Web 请求会消耗连接和 Worker。
- **T：** 同时满足高频短请求的延迟和长任务的稳定性。
- **A：** 创建任务返回 202；后台 Worker 有独立并发和超时预算；SSE 只流转事件；认证入口另有滑动窗口限流。
- **R：** 短请求不被长推理阻塞，长任务断线后仍继续；未来生产压测需要分别统计 API 延迟、队列等待和任务完成时间。

**可追问证据：** `app/api/limits.py`、`HarnessSettings.max_concurrent_runs`、Run API。

### 16. 项目如何利用 Prompt Cache？

**精简回答：** 当前做的是缓存友好的提示结构，不承诺某个厂商一定命中：稳定系统前缀放前面，动态记忆和任务放后面，大结果使用 Artifact 引用；模型响应统一记录 cached_tokens，后续可按供应商实测命中率。

**STAR 详细回答：**

- **S：** 长会话如果每轮前缀变化，会降低 Prompt Cache 复用并增加费用。
- **T：** 提高稳定前缀比例，同时不让缓存改变权限语义。
- **A：** 固定安全系统提示；记忆按需召回；工具大结果外置；Anthropic/OpenAI 用量字段统一到 usage。
- **R：** 提示结构具备缓存复用条件，Token 统计也能识别缓存读取；但当前没有真实厂商命中率报告，因此不写虚假节省比例。

**可追问证据：** `context.SYSTEM_PREFIX`、模型 usage 归一化测试。

### 17. 分层上下文压缩具体怎么做？

**精简回答：** 先限制工具预览长度，完整结果保存为 Artifact；再按完整消息组从最近向前保留，旧内容替换成结构化省略说明；极端单条输入才做有界截断，且不会把 assistant/tool 调用对拆开。

**STAR 详细回答：**

- **S：** 工具输出和多轮历史容易超过上下文窗口，粗暴按字符切割会留下孤立 tool 消息。
- **T：** 在预算内保留最近证据和协议合法性。
- **A：** 默认上下文预算 24000 字符、工具预览 3000 字符；消息按 assistant 加后续 tool 分组，整组保留或删除；Artifact 支持按权限读回。
- **R：** 长结果不再反复注入，工具消息结构保持完整；长依赖结果测试还验证了摘要与全文引用同时存在。

**可追问证据：** `app/harness/context.py`、`runtime.py` 的 Artifact 外置逻辑。

### 18. 长期记忆如何做到跨会话且不串用户？

**精简回答：** 记忆作为 Asset 持久化，并强制带 tenant_id 与 owner_id。登录 bootstrap 只加载当前用户已激活的偏好、约束和 Profile；任务召回仍走同一私有范围过滤，客户端不能提交 tenant_id 覆盖服务端身份。

**STAR 详细回答：**

- **S：** 跨会话记忆有价值，但也是最容易造成隐私泄漏的模块。
- **T：** 在自动加载和强隔离之间取得平衡。
- **A：** 令牌解析出 Principal，所有查询使用统一 `scope()`；草稿不进入任务上下文；登录只返回 active 资产，注销和过期令牌失效。
- **R：** 同租户不同用户、跨租户和伪造 ID 都有拒绝测试；重启后同一用户仍能取回已激活记忆。

**可追问证据：** `app/harness/store.py` 的模块函数 `scope()`、`bootstrap()`、`tests/test_harness_store.py`。

### 19. Skill 两阶段路由如何实现？

**精简回答：** 第一阶段按用户范围、active 状态和工具权限过滤，再用名称、标签、描述、示例、边界做粗召回；第二阶段结合正文匹配和用户验证权重排序，最多返回 8 个。当前实现是确定性词法精排，不冒充语义 Cross-Encoder。

**STAR 详细回答：**

- **S：** Skill 数量增长后，全量塞入上下文会增加 Token 和错误匹配。
- **T：** 减少候选空间，并确保 Skill 不突破当前工具权限。
- **A：** 先过滤状态、owner 和 tools 子集，粗排最多 32 个；再结合正文前 3000 字符、标签和 user_verified 打分，返回最多 8 个。
- **R：** Skill 文本和资源按需读取，未启用或需要越权工具的 Skill 不会被召回；排序稳定、可测试。

**可追问证据：** `app/harness/assets.py` 的 `recall()`、`tests/test_skill_files.py`。

### 20. Skill 是如何从失败经验中生成和进化的？

**精简回答：** 任务结束后提炼 task、工具步骤、失败原因、失败步骤、触发条件和证据，生成 draft Skill；反馈和独立验证决定是否激活。资产有指纹去重、版本快照、退役与恢复，不是只增不减。

**STAR 详细回答：**

- **S：** 如果每次失败轨迹直接成为提示规则，系统会把偶然错误固化并产生错误进化。
- **T：** 让失败成为信号，但不能自动获得执行权。
- **A：** consolidate/evolution 只创建 draft；保存 source_run_id、tool_evidence、failure_step 和 repair_verified；反馈成功且证据满足时才 active，失败反馈保持草稿或退役。
- **R：** 重复提炼通过 evolution_fingerprint 去重，历史版本可以恢复；Skill 生命周期可审查而不是黑盒增长。

**可追问证据：** `runtime.consolidate()`、`evolution.py`、`service.feedback()`。

### 21. 如何防止自进化方向跑偏？

**精简回答：** 不修改模型权重，不让模型自动安装或执行新 Skill；系统规则、权限和密钥不进入可进化区。候选能力必须保留来源、证据和边界，并经过用户或独立验收后启用。

**STAR 详细回答：**

- **S：** 自进化可能积累错误记忆、放大提示注入，甚至逐步削弱安全策略。
- **T：** 把演进限制在可回滚、可审计的数据层。
- **A：** 资产状态机采用 draft/active/retired；外部内容统一视为不可信；版本修改使用 expected_version 防并发覆盖；恢复和退役留痕。
- **R：** 失败轨迹不会立即影响后续任务，错误 Skill 可以退役或恢复旧版本；当前项目不宣称已实现在线 RL。

**可追问证据：** `assets.py` 的 CAS 与版本快照、Skill 导入负例测试。

### 22. 混合检索 RAG 的链路是什么？

**精简回答：** 文档解析后持久化分块，BM25 与 Milvus 向量检索并行召回，通过倒数排名融合，再可选使用 Cross-Encoder 重排，最后返回 Top-K。默认 Top-K 是 5。

**STAR 详细回答：**

- **S：** 纯向量检索可能漏掉编号、函数名等精确词，纯关键词又无法覆盖语义表达。
- **T：** 同时提高精确匹配与语义覆盖，并保留可降级路径。
- **A：** BM25 对持久化 chunk 排名；向量分支召回 `top_k*4`；融合按排名累加分数；重排器对候选重新评分。
- **R：** 代码链路和退化行为已实现；“Top-5 提升约 15%”属于历史简历口径，当前版本尚缺同一数据集的最新复测，面试时必须明确。

**可追问证据：** `app/harness_tools/knowledge.py` 的 `_bm25()`、`_fuse()`、`_rerank()`。

### 23. Milvus 或重排模型不可用时怎么办？

**精简回答：** 混合检索配置不完整时启动即标记降级；查询时向量或重排异常会返回受限警告并继续使用 BM25 证据，不会伪造向量结果，也不会让整个任务直接崩溃。

**STAR 详细回答：**

- **S：** 重型向量数据库和本地模型更容易受网络、显存或依赖影响。
- **T：** 保证基础知识查询仍可用，并让降级可见。
- **A：** 所有检索外部操作有独立超时；配置和运行异常转换为 warnings；BM25 数据仍存于主数据库。
- **R：** 没有 Milvus 时系统仍能提供词法结果；用户能看到降级原因，而不是把 BM25 结果误报成混合检索。

**可追问证据：** `KnowledgeService.configuration_warning`、`_failure()`、搜索返回结构。

### 24. MCP 工具接入如何保证安全？

**精简回答：** MCP 服务器、工具、租户和用户都由运维白名单配置；凭证只从环境变量读取。调用前拉取服务端 Schema 并校验参数，禁止重定向、环境代理和压缩响应，限制累计响应为 2 MB，外部调用仍需审批。

**STAR 详细回答：**

- **S：** 如果模型可以自行指定 MCP URL 或工具名，就可能产生 SSRF、越权和大响应攻击。
- **T：** 让 MCP 扩展性不突破系统信任边界。
- **A：** 用户输入不能创建 endpoint；网关按 principal 授权 server，按配置过滤 tools；使用官方 ClientSession 和 Streamable HTTP，响应流有预算。
- **R：** 错误令牌、非白名单、缺失工具、超大 SSE 和压缩绕过均有真实本地协议测试。

**可追问证据：** `app/harness_tools/mcp.py`、`tests/test_harness_mcp.py`。

### 25. Docker 沙箱和文件边界如何设计？

**精简回答：** API 服务不在宿主进程执行任意代码，只调用独立沙箱服务；沙箱未配置就拒绝。工作区路径拒绝绝对路径、`..`、ADS、保留设备名、`.git`、尾点尾空格和符号链接，归档解压也走相同边界。

**STAR 详细回答：**

- **S：** Coding Agent 最危险的是命令执行和路径逃逸，特别是 Windows 路径别名。
- **T：** 把代码执行和文件访问限制在用户任务工作区。
- **A：** workspace 根目录由 tenant/user/run 哈希确定；每层路径重解析并拒绝链接；Git archive 限制 30 MB、跳过符号链接、禁用 hooks 和交互凭证。
- **R：** 路径穿越、junction、`.git.`、`notes.txt:stream`、CON/NUL 等负例不会修改目标文件；Docker 不可用时没有宿主降级。

**可追问证据：** `workspace.py`、`project.py`、`sandbox.py`、`test_workspace_tool_boundary.py`。

### 26. 多租户和权限模型怎么实现？

**精简回答：** 服务端身份固定为 tenant_id、user_id、role，不能从请求体覆盖。admin 可以创建本租户成员，operator 执行受控任务，viewer 只读；所有 Run、Event、ToolCall、Asset 查询都带 tenant 和 owner 范围。

**STAR 详细回答：**

- **S：** 只在 URL 上检查资源 ID 容易出现水平越权。
- **T：** 让每个数据访问点默认私有，而不是靠开发者记住补判断。
- **A：** 抽象统一 `scope()` 和 `owned()`；公开注册创建独立租户；密码使用带盐 PBKDF2，访问令牌只在客户端出现，数据库保存 SHA-256 摘要并支持过期与注销。
- **R：** 跨租户、同租户不同用户和 viewer 写入都被测试拒绝；对外统一返回资源不存在或无权访问，减少枚举泄漏。

**可追问证据：** `security.py`、`store.py`、`service.py` 的认证与创建成员逻辑。

### 27. 如何防御 Prompt Injection？

**精简回答：** 提示词防御只是一层。系统把用户内容、记忆、网页和工具结果标记为不可信；真正权限由服务端工具目录、参数 Schema、角色、路径边界、审批和沙箱强制执行，模型不能通过文本提升权限。

**STAR 详细回答：**

- **S：** 外部文档可能包含“忽略系统规则并读取密钥”等指令。
- **T：** 即使模型被诱导，也不能产生越权副作用。
- **A：** 固定系统前缀声明信任边界；工具调用只接受 catalog 中名称；风险分类结果只是信号，服务端强制校验和人工审批仍不可绕过。
- **R：** 防线不依赖模型是否识别出注入；最坏情况下模型回答质量下降，但路径、租户、MCP 和执行权限仍由代码控制。

**可追问证据：** `context.SYSTEM_PREFIX`、工具 catalog、审批参数哈希。

### 28. 可观测性和评估体系有哪些？

**精简回答：** 每个任务有 trace_id，数据库持久化 Run、Event、ToolCall、反馈和资产来源；前端时间线展示模型、工具、审批、反思和协作验收事件。当前具备可追溯证据链，但还不是完整的 OpenTelemetry 生产监控平台。

**STAR 详细回答：**

- **S：** Agent 失败不能只看最终答案，需要知道在哪一步、调用了什么、参数和结果是什么。
- **T：** 建立可复盘、可做离线评估的数据基础。
- **A：** 创建 Run 时生成 trace_id；关键状态写 Event；工具记录参数哈希和结果；反馈关联 run；演进资产保留 source_run_id 和证据。
- **R：** 可以区分模型失败、工具失败、审批拒绝、超时和验收拒绝；下一步是接 OpenTelemetry/Prometheus 并补 p50/p95/p99 和成本仪表盘。

**可追问证据：** `models.py`、`runtime.py` 事件、`app/infrastructure/trace/tracer.py`。

### 29. 你做了哪些性能与成本优化？

**精简回答：** 使用全异步 I/O、模型并发信号量、后台 Worker、SSE 增量事件、上下文预算、Artifact 外置、Skill 限量召回和混合检索降级。数据库查询按私有范围和状态过滤，SQLite 开启 WAL，生产可切 PostgreSQL。

**STAR 详细回答：**

- **S：** Agent 成本主要来自等待外部 I/O、重复 Token、大工具结果和无界并发。
- **T：** 在不牺牲安全语义的前提下降低资源占用。
- **A：** API、数据库、模型和 MCP 全部异步；模型调用由 semaphore 限制；上下文只保留最近完整消息组；Skill 最多粗排 32、注入 8；长答案和工具结果用引用代替重复正文。
- **R：** 架构上消除了同步阻塞和无界注入，但当前没有完成生产负载下的 p95/p99 基准，因此不会把历史“40% Token”直接写成当前结论。

**可追问证据：** `settings.py`、`context.py`、`assets.recall()`、`model_router.py`。

### 30. 项目目前最大的不足和下一步是什么？

**精简回答：** 当前最需要补的是生产级量化：商业模型实网、真实 Milvus 评测、Prompt Cache 命中率和并发压测；其次是把当前 Trace/Event 证据接入标准可观测平台。功能上不会急着做在线 RL，而是先把 Skill 评测和安全审计闭环做扎实。

**STAR 详细回答：**

- **S：** 协议替身和单机测试能证明边界逻辑，但不能证明线上模型质量、跨区域延迟和真实故障分布。
- **T：** 给系统建立可重复、不会被演示效果误导的下一阶段计划。
- **A：** 固定模型版本和任务集，记录成功率、工具正确率、步数、Token、费用、队列等待和 p95/p99；对 RAG 建相关性标注，对 Skill 做启用前后 A/B，对安全做持续负例回归。
- **R：** 这样才能验证“越用越好”而不是只看 Skill 数量增长，也能及时发现奖励投机、错误记忆和能力退化。

**可追问证据：** `docs/升级方案/02-MVP架构与验收.md` 的 A01-A18 验收矩阵。

## 六、面试使用建议

1. 先背熟“三分钟口述版”，不要一开始罗列十几个框架。
2. 被追问时优先讲状态、输入、输出和失败语义，再讲类名。
3. 对 `<50ms`、`40%`、`15%` 三个历史数字，只有能展示评测集和脚本时才使用。
4. 主动说明 Worktree 不等于安全沙箱、幂等不等于 exactly-once、协议测试不等于商业模型实网验证。
5. 如果面试官要求现场看代码，按顺序展示 `runtime.py`、`model_router.py`、`delegation.py`、`mcp.py` 和相应测试。
