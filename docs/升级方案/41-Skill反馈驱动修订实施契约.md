# Skill 反馈驱动修订实施契约

> 执行方式：沿用已授权第15号方案、第23号能力内核补齐任务与 subagent-driven-development；先实施草稿生成，再独立规格和质量审查。后台已通过双审查、60项专项及902项完整回归，详见[第42号记录](42-Skill反馈修订与幂等验收.md)；前端审阅按第44号继续实施，0.2.9安装包不含此增量。

日期：2026-10-07。

**目标：** 将终态任务的失败反馈关联到本次实际召回的 Skill 版本，自动提出私有修订草稿；保留原技能和原权限，不把推测的失败原因当作事实。

**架构：** 复用持久任务、反馈、召回事件和资产版本。反馈事务仅登记有界修订请求，独立后台模块通过数据库比较更新领取租约；模型仅生成纯文本建议，保存前再次检查所有者、当前角色、反馈指纹、租约及技能版本。生成和结果事件同事务提交。无需新增数据库表、任意代码执行入口或客户端权限。

**技术栈：** Python、FastAPI、SQLAlchemy async、SQLite／PostgreSQL SQL契约、现有模型路由与共享模型容量门。真实 PostgreSQL 本批独立验证，环境不可用时标记未验证。

## 代码现状及差距

- `service.py:create_run` 已发布 `assets_recalled` 事件，包含服务端生成的资产 ID 和版本；它是“曾进入上下文”的证据，不能证明模型实际使用或技能导致失败。
- `evolution.py:EvolutionWorker` 已从成败轨迹生成最多4项新草稿；`evolution_state` 完成后不再因后续反馈重跑。
- `service.py:feedback` 已保存反馈，现有激活逻辑不能验证提炼后新增的步骤，也未把反馈映射到被召回技能的修订。
- `assets.py` 已有版本快照、修订清除验证标记及退役。新机制应在这些边界内生成独立草稿，不能覆盖活动版本。

## 方案选择

| 方案 | 优点 | 成本与问题 |
|---|---|---|
| 推荐：按实际召回版本生成修订草稿 | 复用现有表和审阅界面；保留原活动技能；能追溯反馈和版本 | 人工审核前不影响新任务；另需重新验证流程 |
| 直接覆盖或自动启用活动技能 | 立即改变策略 | 易污染有效经验；无法把相关性当因果，故不采用 |
| 每次反馈重新提炼全部轨迹 | 实现表面简单 | 重复模型成本、重复草稿，无法明确修订对象，故不采用 |

本期仅完成第一方案的请求、租约、提炼和草稿保存。重新验证及按验证结果替换原活动技能是后续独立交付，不给草稿标注“已修复”。

## 模块与输入输出

| 文件 | 职责 |
|---|---|
| `app/harness/skill_revision.py`（新增） | 反馈请求登记辅助、租约、来源选择、纯模型提炼及事务保存 |
| `app/harness/service.py` | 原反馈事务内登记修订，不同步等待模型，不改变运行终态 |
| `app/harness/evolution.py` | 既有后台生命周期内调度修订，避免额外无限循环和并发膨胀 |
| `app/harness/assets.py` | 保护新增来源元数据，保持人工编辑清除验证的现有行为 |
| `app/harness/store.py` | 修复关联缺陷：仅真实终态事件迁移计划状态，反馈与后台事件保留完成状态 |
| `tests/test_skill_feedback_revision.py`（新增） | 真实 Store 与可控模型验证隔离、竞态、格式、幂等与草稿门 |
| `docs/技能反馈修订指南.md`（新增） | 失败反馈如何产生草稿、如何审阅及本期能力边界 |

输入为本人终态 Run、反馈 `success=false` 和最多8项服务端召回版本引用。只考虑本人 `kind=skill` 且当前仍活动、版本与召回记录一致的技能；来源不存在、畸形、跨用户、已退役或版本变化时跳过。最多选2项修订，原技能正文、工具结果和反馈进入有界低信任模型输入，不能提供系统权限、凭据或任意宿主文件。

输出为独立 `draft` Skill 资产，其元数据关联原资产 ID／版本、反馈任务 ID／指纹、来源工具证据和生成指纹。保留原技能必要工具集合，不能接受模型新增或删除权限需求。文本必须说明触发条件、建议步骤、边界和验证办法；“尚未验证”由服务端记录。保留原 `active` Skill 的内容、版本及状态。

## 请求与恢复契约

1. 相同终态任务、相同失败反馈内容产生同一请求指纹；包括A→B→再次A的非连续重复，提交不重新扣模型成本、不新增草稿。反馈内容发生变化形成新请求，历史草稿保留来源，不被误当新反馈的结果。
2. 活跃、等待审批、取消和中断任务不生成修订；支持现有反馈入口的兼容行为，修订逻辑不能提前结束或执行任务。
3. 修订请求状态为 `queued/started/done/skipped`；可使用 Run.config 下独立命名空间。领取与封口必须比较请求指纹、租约所有者和截止时间，两个 Store 竞争只有一方有效领取。
4. 失去租约的旧 Worker 不能保存或覆盖新请求；已保存草稿与结果事件原子提交。进程崩溃后过期请求可恢复模型草稿提炼，这是无工具副作用的工作，不重放原任务工具。
5. 超时、无模型、非法 JSON、超长或未知对象记录可理解的跳过结果，原任务与技能继续可用。结果不重试无限循环，不输出模型隐含推理或风险正文。
6. 保存前重新检查当前用户角色与所有者。只读降权后不保存候选；反馈已改成成功或版本已改时丢弃过期模型输出。
7. 原 Skill 正文和反馈是低信任数据。纯生成调用不提供工具；模型不能创建系统记忆、修改风险策略、自动安装工具或验证自身建议。
8. 反馈、原经验提炼和修订作业同时更新 Run.config 时，必须保留其他命名空间的字段。沿用用户行锁并在取得锁后重新读取任务；原提炼领取阶段也要遵守相同顺序，避免不同 Store 的旧配置覆盖新请求。模型调用期间不持有事务锁。

模型输出采用固定 JSON 契约：`{"revisions":[{"asset_id":"选中的原技能ID","content":"未验证的修订建议"}]}`，最多2项。外层和每项只允许这些字段，拒绝重复JSON键，ID必须对应本次选中来源且不得重复，正文非空、最多8000字符，原始回复最多20000字符。来源版本须为SQL整数范围内的正整数，畸形巨值不进入数据库绑定。模型不决定名称、状态、来源、版本或工具集合。非资源元数据仍遵守既有8192字节上限；无法在原工具依赖及来源预算内保存时记录跳过，不能通过丢弃必需工具放宽限制。

## 分步验收

- [x] **一：真实红例。** 活动 Skill 被新任务召回后，任务终态收到失败反馈，要求修订模块生成关联原版本的草稿；原实现应无此草稿。
- [x] **二：最小闭环。** 接入反馈登记、后台领取和有界提炼；原活动 Skill 不变，候选不参与召回，登录不自动启用。
- [x] **三：证据负例。** 无召回记录、伪造引用、异租户、同企业不同用户、非 Skill、版本不一致、已退役、仅用户自称用了技能，均不能成为修订来源。
- [x] **四：并发与恢复。** 相同反馈重复提交、不同反馈覆盖、双 Store 竞争、过期租约、保存前降权或原技能改版；旧输出不能污染新请求，草稿去重，结果事件与资产一致。
- [x] **五：困难模型输入。** 提示注入、空列表、未知字段或类型、超长正文、含工具权限修改建议、失败原因臆测；输出严格拒绝或保留为未验证建议，不改变工具权限。
- [x] **六：简化与双审查。** 实际应用 code-simplifier；规格审查通过后质量审查；专项、现有资产修订／召回／经验提炼和合适集成回归全部退出0。
- [ ] **七：用户文档与 Git。** 指南说明草稿审阅入口及来源字段；第23号仅更新已验证范围。中文功能和文档提交分组推送，独立核对远端。不覆盖0.2.9冻结发布资产。

## 交付界限

本期证明“反馈关联召回版本，自动提出修订草稿”，不证明技能导致任务失败、不证明修订有效，也不自动更新模型权重。后续重新验证必须使用真实新任务和证据门，并明确区分结构通过、人类确认与独立测试通过；不得用本期用户反馈填充 `repair_verified=true`。
