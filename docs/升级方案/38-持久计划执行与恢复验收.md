# 持久计划执行与恢复验收

日期：2026-10-07。基线提交：`3bdd05b`。承接[第36号实施契约](36-持久计划节点与结果验收实施契约.md)，新增源码能力不包含在公开0.2.9冻结下载包中。

## 实际交付

- `plan_runtime.py`管理可信计划、节点执行、结果验收、一次重规划与有界降级；原子保存节点推进与模型结果消费，首节点答复不能提前结束运行。
- `runtime.py`按模型用途和节点修订绑定完整结果，规划阶段的工具调用在检查点恢复后仍禁止执行；原ReAct与旧运行保持兼容。
- `store.py`在执行事务内核对自身有效租约，过期执行器不能消费结果、收费或改变终态。
- `service.py`的委派预检及创建共同预留父任务验收、后续节点和封口预算；批准入口不能覆盖已有风险拒绝。
- 持久事件提供计划快照、节点开始／验收、重规划与历史工具来源；状态查询不公开内部模型配置，工作台专用节点展示另依第39号契约验收。

新计划默认共享10动作，最多8节点；两节点纯回答实际需6动作。规划、重规划、节点模型、风险模型、新工具启动、确定性验收和最终交付计费，等待审批与消费已保存结果不重复收费。最终回答上限131072字符；这属于工程限制，不是性能提升指标。

## 独立审查发现与修复

首次规格审查要求修改：最终工具证据摘要131073字符仍能完成；风险审查拒绝已持久化后，崩溃恢复曾跳过拒绝并进入人工审批。第二项来自基线已有逻辑，本批同时关闭，不能描述为本批新引入的回归。

修复后，新返回与已存摘要统一验证类型、非空及长度；执行预检、工具启动、历史来源复用和批准入口均重施持久风险拒绝。批准失败仍允许用户选择拒绝并取消任务。

首次质量审查另复现两个重要遗漏：初规划无效后的降级回答仍可超长；17个工具调用直到第17个证据绑定才失败，前16个已执行。旧冻结全量回归因此在中途主动停止，不作为通过记录；修复要求为所有降级封口统一文本边界，以及新响应／恢复预检在首个副作用前拒绝超限批次。

第二轮修复统一降级回答的类型、长度和结果身份检查，并在封口事务内重新读取；工具批次统一最多16项，在过滤已完成调用前核对整轮。非法规划工具批次保留拒绝标记后走原降级路径，不保存可执行调用。实施侧新增24项边界通过，独立双复审和主控新全量仍按下方检查项完成后记录。

恢复兼容复审再发现：原始重规划检查点保留超限批次时，外层工具检查抢先返回422而未进入安全降级。已将已有结构计划优先路由到计划处理，新响应和原始检查点均保留必需工具门，非法调用不执行；新增四项边界与相关16项限定回归通过。现代新检查点已归一拒绝标记，兼容测试另外覆盖未归一的旧形态。
