# 0.2.5 验收记录

## 读取性能

根因：工作台列表、详情、事件所有权检查和文件所有权检查使用完整 ORM 行，重复读取并解码内部 `messages`，其大小会随任务增长。现在公开状态使用列投影，事件和文件检查只查询带租户及用户范围的 ID；Worker 执行链仍读取完整上下文。

新增 `tests/test_run_read_projection.py`，修复前因为查询包含 `messages` 失败；修复后公开字段完全一致、分页和事件游标正确，同租户另一成员无法读取任务、事件、文件或利用游标探测任务。

2026-10-04 本机临时 SQLite，固定 2 MiB 内部上下文、各 50 次相同状态读取，交替执行完整行基线与投影读取：

| 读取方式 | 中位延迟 | P95 |
|---|---:|---:|
| 完整行 | 16.535 ms | 24.281 ms |
| 状态投影 | 9.871 ms | 18.529 ms |

该负载下中位延迟减少 40.30%。复现命令：`python -m scripts.read_performance_acceptance`。这是数据库读取微基准，不含模型调用，不代表 Redis 缓存、Token 节省或生产任务吞吐。

## 真实 PostgreSQL 与 Docker

从干净提交 `32a9562` 加载源码，在旧验收镜像提供的依赖环境中，只读挂载源码到独立容器；数据库为新建的专用 `aegis_acceptance_025`，未对正式数据库写入。

两实例的 20 请求幂等、审批竞争、重启恢复、取消后审批和未知副作用停止均通过。模型为 20ms 确定性替身，固定原脚本的密集轮询负载：

| 任务数 | P95 完成时间 | P95 队列等待 | 吞吐（任务/秒） | 错误 |
|---:|---:|---:|---:|---:|
| 10 | 3.2186s | 2.2007s | 3.1 | 0 |
| 50 | 45.2046s | 34.8441s | 1.1 | 0 |
| 100 | 70.8016s | 52.3911s | 1.4 | 0 |

没有降低轮询频率。上述任务耗时包含数据库排队与本机同时构建安装包的资源竞争，没有与旧版建立相同环境的 A/B，不能据此宣称吞吐提升；高负载的队列等待仍需改进。

真实 Docker 沙箱再次通过：非 root、宿主密钥不可见、工作区只读、禁网络、临时目录可写、无限循环超时回收。wheel 0.2.5 已在独立虚拟环境完整安装依赖，并通过静态 hash、登录、能力接口、重启后偏好保留验收。
