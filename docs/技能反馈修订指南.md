# 技能反馈修订指南

终态任务收到失败反馈后，系统可以为本次实际召回的 Skill 版本生成独立、私有、未验证的修订草稿。召回只证明 Skill 进入任务上下文，不能证明实际使用，更不能证明它导致失败。

## 操作与结果

当前源码增量在已完成或失败任务的审查区提供“反馈说明（可选）”。填写遗漏、约束、期望或验收依据，再点击“仍有问题”或“已解决”；留空兼容原有按钮。说明按原 API 的 Unicode 码点最多 4000 字符计数，表情也计一个字符。保存失败时保留输入并就近提示；保存成功、切换任务、开始新任务、退出或换账号时清空。同一任务重新读取，或临时进入技能库后返回该任务，保留未提交说明和有效错误。异步提交绑定点击时选中的任务及当前读取代次，旧响应不能覆盖新任务或同任务新代次的说明。

以上交互使用既有 `POST /api/v1/runs/{run_id}/feedback` 的 `success` 与 `note`，没有新增 API。后台经验服务启用时，会处理反馈修订请求；原有成功或失败轨迹的经验提炼仍可继续。0.2.10的便携包、Setup与wheel已分别通过本功能安装验收；0.2.9保持旧能力，不因新版发布而改变。产物与公开下载状态见[0.2.10验收记录](升级方案/47-0.2.10安装与公开发布验收.md)。

在“技能库”查找新增候选。只有符合服务端来源元数据契约的草稿标为“修订草稿”，并显示“基于原技能vN，未验证建议”。普通、导入及已启用的历史技能保持原有操作。草稿沿用原 Skill 名称；“查看来源任务”打开收到失败反馈的任务，版本记录保留原资产 ID、原版本和召回证据。草稿与原资产是两个独立 ID。

展开“对照原技能”才会读取本人原技能，展示原文与未验证建议。原 ID、类型、活动状态、版本和来源仍匹配时才能展示原文；若版本变化、退役或来源不符，则提示“原技能已变化”，不拿当前正文冒充生成时的历史版本。404 或 403 仅提示无法读取或无权限，网络失败保留建议并提供“重试读取原技能”，反复收起展开不会自动重复请求。切视图、筛选、刷新或换账号后，过期返回不会回填新条目。

对照正文使用纯文本，并有界显示前 8000 个字符；截断时有可见说明，可通过现有正文入口继续核对。页面不解释正文中的 HTML，不读取任意 URL 或任务配置。原生折叠标题在异步更新时保留展开和焦点，深浅主题与窄屏沿用原有样式。修订事件显示“记录技能修订建议”，草稿完成不代表修复成功。启用、退役、正文修订、来源任务和版本记录仍由原服务端权限控制，不自动批准工具操作。

原活动 Skill 的内容、版本、状态、必要工具和权限保持不变。修订草稿继承原工具集合、文本资源、目录与边界信息，且记录失败任务的工具限制。草稿不会参加召回、不会在登录时启用，也不会自动替换活动 Skill。`repair_verified` 始终为 `false`；本期不执行修订重验，不提供新的公开 API 或数据表。

## 可信来源门槛

服务端仅使用该任务保存的 `assets_recalled` 事件，检查最多前 8 个引用，从中选择最多 2 个本人、同租户、仍活动且版本一致的 `kind=skill` 资产。事件顶层 `source_run_id` 必须是本任务；资产引用中的 `source_run_id` 必须与原资产元数据一致，其来源任务也必须仍属于本人、同租户。

以下情况会跳过：缺少可信事件、版本或来源任务；引用格式畸形；非 Skill；已退役；版本已改变；来源任务或资产属于其他用户/租户。即使同企业也不能使用其他用户的资产。普通手写 Skill 缺少服务端来源时，不作为本功能修订来源；用户在反馈中自称“使用了技能”不构成证据。

保存前再次检查当前用户及角色、失败反馈哈希、来源任务、原 Skill 活动状态及版本、请求指纹和租约。生成期间反馈改为成功、角色降为只读或原资产改变时，旧建议不会保存。模型调用期间不持数据库事务锁，也不重放原任务的任何工具。

## 有界生成与幂等

模型只接收有界的低信任原技能、任务、反馈和工具证据，经过现有共享模型容量门。该调用不提供工具。模型只能返回以下 JSON，不得附加名称、权限、工具、来源、状态或版本字段，也不能输出隐含推理：

```json
{"revisions":[{"asset_id":"选中原ID","content":"未验证修订建议"}]}
```

最多 2 项，ID 必须已选中且唯一，正文非空、最多 8000 字符，完整回复最多 20000 字符。空列表可正常跳过；额外字段、重复 JSON 字段、错误类型、超长回复、未选 ID 都拒绝保存。正文中出现权限或激活建议不会改变服务端权限与草稿状态。

相同终态任务与相同失败反馈指纹只处理一次，包含 A→B→再次 A 的非连续重复；历史终态结果保存在私有事件中，不在运行配置累积无限列表。新失败内容替换当前请求，已保存旧草稿及来源保留。请求状态为 `queued`、`started`、`done`、`skipped`。

数据库条件更新领取请求及封口，绑定 owner、指纹、租约 ID 和截止时间。双 Store 只允许一方领取；进程崩溃后过期请求可重新进行纯文本生成，旧 worker 不能污染新租约或新反馈。缺少模型、超时、坏格式等终止为 `skipped`，不会无限重试，也不修改原任务终态。

领取时同时保存已开始处理的指纹。若A仍在生成时用户提交B再提交A，已被替换的在途A记录为跳过，不重新调用模型，也不接受旧作业输出；需要新建议时提交不同的具体说明。未被新反馈替换的当前请求仍支持过期租约恢复，两者不能混为同一重试。

元数据沿用 Skill 非资源部分 8192 字节上限。必要工具、原边界、资源或服务端来源放不下时跳过，不裁掉工具来放宽限制。服务端保护 `source_run_id`、原 ID/版本/来源、反馈哈希、修订指纹、召回证据与任务权限边界；客户端不能伪造或改写，人工编辑后仍保留这些来源与必要工具。

## 实现与验证边界

反馈在同一事务写入 `Run.config.skill_revision`。反馈、原经验提炼与技能修订使用统一顺序：先取得用户行锁，再重读 Run 并合并各自命名空间。SQLite 使用 `BEGIN IMMEDIATE` 处理跨 Store 写竞争；PostgreSQL 使用用户行条件更新取得行锁，并在锁后刷新运行。草稿、版本快照和结果事件原子提交。反馈/提炼事件不会把已完成的计划改为阻塞。

自动化专项使用真实 SQLite Store、双 Store 与可控纯模型，包括真实工具执行沉淀、成功反馈激活、未经改写的召回事件及失败反馈修订闭环。模型真实服务与独立 PostgreSQL 实例本轮未验证，未连接业务数据库；SQLite 验证结果不能代替 PostgreSQL 集成验收。
